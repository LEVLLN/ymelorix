# ymelorix

## О чём проект

Консольный загрузчик избранного из Яндекс Музыки. Репозиторий называется **ymelorix**.

Имя собрано из двух частей. `YM` — Yandex Music, привычное сокращение, по которому сразу
понятно, откуда берутся данные. `Melorix` — melody плюс суффикс `-ix` в духе технологических
стартапов: он превращает обычное слово в имя продукта и не тянет за собой чужих ассоциаций.

Выбор был практическим, а не только звучным. Слово короткое, читается с первого раза и
одинаково пишется на слух и глазами — не нужно диктовать по буквам. Оно свободно как домен
и как одинаковый ник в социальных сетях, а это важнее красоты: имя, занятое наполовину,
разъезжается по площадкам и перестаёт быть узнаваемым.

Название неофициальное и с Яндексом никак не связано — это личный проект поверх
неофициального API.

Что он делает: выгружает список любимых треков из Яндекс Музыки — берёт идентификаторы из
`likes/tracks`, добирает названия и исполнителей батчами через `POST /tracks` и печатает их
в stdout. С API он разговаривает через крейт
[`yandex-music`](https://github.com/vyfor/yandex-music-rs) — именно этот, обёртку над API
мобильных клиентов. Мимо него ходят только проверка авторизации и сами файлы; почему — сказано
ниже.

```
$ cargo run -- list-favorites
Избранных треков: 342
Radiohead — Weird Fishes / Arpeggi [5:18]
...
```

## Быстрый старт

Установка из репозитория:

```sh
cargo install --git https://github.com/LEVLLN/ymelorix
```

```sh
export YANDEX_TOKEN=<токен>
ymelorix list-favorites
```

Из клона репозитория, без установки, — то же самое через `cargo run`:

```sh
export YANDEX_TOKEN=<токен>
cargo run -- list-favorites
```

Токен выдаётся по OAuth-флоу официального клиента Музыки и подойдёт не любой — как получить
нужный, описано в [docs/token.md](docs/token.md).

## Команды

| Команда | Что делает |
| --- | --- |
| `list-favorites` | Печатает все избранные треки |
| `download-favorites [-p DIR] [-q QUALITY] [-u]` | Скачивает все избранные треки |
| `download-track <URL> [-p DIR] [-q QUALITY] [-u]` | Скачивает трек по ссылке |
| `download-link <URL> [-p DIR] [-q QUALITY] [-u]` | Скачивает альбом или плейлист по ссылке |

```sh
cargo run -- download-favorites --path ~/Music            # скачать весь список заново
cargo run -- download-favorites --path ~/Music --update   # дозакачать недостающее
cargo run -- download-favorites --path ~/Music -q normal  # с потерями, экономно
cargo run -- download-track https://music.yandex.ru/album/4147089/track/33898323 -p ~/Music
cargo run -- download-link https://music.yandex.ru/album/4147089 -p ~/Music
cargo run -- download-link https://music.yandex.ru/users/yamusic-daily/playlists/1234 -p ~/Music -u
```

`--path` (`-p`), `--quality` (`-q`) и `--update` (`-u`) работают одинаково у всех трёх команд
загрузки. `--path` — директория для файлов, создаётся при необходимости, по умолчанию текущая.

Ссылку `download-track` понимает в любом виде: `album/<id>/track/<id>`, `track/<id>` или просто
идентификатор трека.

### Альбом и плейлист

`download-link` берёт ссылку двух видов — со схемой и без, с параметрами и якорем:

| Что | Ссылка |
| --- | --- |
| Альбом | `https://music.yandex.ru/album/<id>` |
| Плейлист | `https://music.yandex.ru/users/<владелец>/playlists/<номер>` |

Владельцем в ссылке стоит логин (`yamusic-daily`) или числовой `uid` — годятся оба. Ссылку
такого вида даёт кнопка «Поделиться» внутри плейлиста; короткая форма
`music.yandex.ru/playlists/<uuid>` не поддерживается — ручке API нужны владелец и номер,
а взять их из uuid неоткуда. Ссылка на трек тоже отвергается, с указанием на `download-track`:
молча скачать альбом вместо трека — не то, чего просили.

Треки альбома идут в порядке диска, треки плейлиста — в порядке плейлиста. Правила имён,
пропусков и перезаписи те же, что у избранного; одноимённые треки внутри одной подборки так же
делят имя файла.

`--update` (`-u`) — **дозакачивание**. С этим флагом перед работой снимается список файлов
в директории, и трек, который там уже есть, не качается заново. Без флага скачивается весь
список целиком, а существующие файлы перезаписываются.

Сверка идёт по имени без расширения: расширение известно только из ответа API, поэтому иначе
за каждый пропускаемый трек пришлось бы платить запросом. Побочное следствие — файл, скачанный
в другом качестве, считается тем же самым и заново не качается.

Имя файла — `Исполнители - Название.<расширение>`; запрещённые в ФС символы заменяются на `_`,
длина ограничена по байтам. Идентификатора в имени нет намеренно, ради читаемости. Плата за
это: два разных трека с одинаковым названием делят имя, и внутри одной выгрузки второй
перезаписывает первого — с пометкой в выводе и записью `перезаписан файл одноимённого трека`
в логах.

С `--update` повтор команды безопасен и дозакачивает недостающее. Список того, что уже есть,
снимается один раз перед началом работы — поэтому файл, записанный в этом же прогоне, в снимок
не попадает, и одноимённый трек его перезапишет, а не будет пропущен.

## Качество

`--quality` (`-q`) выбирает канал раздачи:

| Значение | Что это | Формат на выходе |
| --- | --- | --- |
| `lossless` (по умолчанию) | Без потерь | обычно `.flac` |
| `normal` | Сжатие с потерями, экономит трафик и место | обычно `.m4a` или `.mp3` |
| `low` | Низкое, для медленной связи | обычно `.m4a` |

Конкретный **кодек** не выбирается: запрашиваются все поддерживаемые, а сервер подбирает
подходящий под запрошенное качество — поэтому расширение известно только из ответа. Ставится
оно по кодеку: `flac` → `.flac`, `mp3` → `.mp3`, а `aac`, `he-aac` и все варианты с суффиксом
`-mp4` → `.m4a` — это звук в контейнере MP4, и `.m4a` для него правильнее, чем `.mp4`, которое
системы читают как видео. Если понадобится жёстко потребовать конкретный кодек, крейт это
умеет, флага пока нет.

Lossless доступен не всем и не всегда: он требует подписки, и на треке без неё сервер отдаст
что есть. Ошибкой это не считается.

**Смена качества не перекачивает уже скачанное.** С `--update` сверка идёт по имени файла без
расширения, поэтому трек, лежащий в lossless, будет пропущен и при запросе `low`, и наоборот.
Чтобы перекачать в другом качестве, качайте в отдельную директорию или без `--update`.

Данные идут в stdout, ход работы — в stderr. Поэтому `list-favorites | grep`
получает треки, а не пополам со служебными строками, а `| head` не роняет команду.

## Поведение при сбоях

Файл сначала пишется рядом под именем `*.part` и лишь потом переименовывается — переименование
в пределах директории атомарно. Оборванная загрузка (Ctrl-C, обрыв связи, сбой питания) не
оставит правдоподобный огрызок, который следующий запуск сочтёт скачанным: на диске окажется
либо целый файл, либо `.part`, который ни на что не влияет и перезаписывается при повторе.

Размер скачанного сверяется с обещанным в ответе — это ловит и обрыв, и страницу с ошибкой,
присланную CDN под видом успеха.

Если основная ссылка не отвечает, перебираются зеркала из того же ответа.

У всех сетевых вызовов есть сроки: 30 с на ответ API, 10 с на соединение и 30 с на паузу
между байтами тела. Дедлайна на файл целиком нет намеренно — lossless-трек на медленном канале
качается законно долго.

При выгрузке списком — избранное, альбом, плейлист — ошибка на отдельном треке не прерывает
работу: неудачи печатаются в stderr, а в конце команда завершается ошибкой с их числом. Из
этого правила три исключения, все означают, что дело не в треке:

- отказ файловой системы — кончилось место, нет прав, директория исчезла — прерывает выгрузку сразу;
- пять неудач подряд прерывают её же: так выглядят истёкший токен или пропавшая сеть,
  и остаток списка только потратит запросы впустую. Счётчик обнуляет только скачанный трек:
  пропуск по `--update` сети не касается и о её состоянии ничего не говорит;
- `429` от раздачи, не отпустивший за три попытки, — про него ниже.

`--help` работает без токена.

### Слишком много запросов (`429`)

Вызовы API повторяются: три попытки с паузами 1 и 2 секунды. Повторяются только чтения —
список лайков и данные треков ничего не меняют, поэтому лишний запрос не может задвоить эффект.
Причина отказа при этом неизвестна: крейт `yandex-music` не отдаёт ни ответа, ни его статуса,
так что повтор одинаково достаётся и троттлингу, и снятому с раздачи треку — отсюда и всего
три попытки.

С файлами иначе: их качает наш собственный клиент, и `429` виден прямо. Такой ответ не
считается отказом трека — запрос повторяется до трёх раз, а если сервер прислал `Retry-After`,
пауза берётся из него. Просьбу подождать дольше минуты уважить нечем: держать процесс — а в
cron ещё и блокировку — в ожидании получаса хуже, чем остановиться.

Если раздача просит сбавить темп и после повторов, выгрузка **останавливается целиком**, не
перебирая ни зеркала, ни остаток списка: квота у них общая, и каждый лишний запрос её только
удерживает. Скачанное уже лежит на диске, поэтому повтор команды с `--update` продолжит
с того же места.

Ограничения темпа запросов у команды нет: треки скачиваются подряд, без пауз между ними.

## Диагностика

Ошибки `account/status` печатаются вместе с телом ответа — именно в нём Яндекс объясняет отказ.

| Симптом | Причина |
| --- | --- |
| `HTTP 401`, тело с `"error":"Unauthorized"` | Токен не распознан: опечатка, истёк или отозван |
| `HTTP 403`, тело с пустым `"result":{}` | Токен выдан приложением, не допущенным к API — перевыпустите его по [docs/token.md](docs/token.md) |
| `в ответе account/status нет uid` | Ответ анонимный: заголовок авторизации не дошёл или проигнорирован |

Схема авторизации имеет значение: Яндекс принимает `Authorization: OAuth <токен>` и **молча
игнорирует** `Bearer`, отвечая на такой запрос анонимным `200` без `uid`. Правильный заголовок
ставит крейт `yandex-music`.

## Безопасность

Токен даёт полный доступ к аккаунту — обращайтесь с ним как с паролем. Держите его только в
переменной окружения, не коммитьте и не вставляйте в логи и issue. Отозвать выданный доступ
можно на [id.yandex.ru](https://id.yandex.ru) → Безопасность → Приложения.

Сам загрузчик токен не печатает: он скрыт в `Debug`, а файлы качаются отдельным клиентом
**без заголовков авторизации** — их отдаёт CDN, и токену там делать нечего. Прямые ссылки
на файлы подписаны и ограничены по времени, поэтому из сообщений об ошибках URL вырезается:
иначе он попал бы в stderr и в JSON-логи, откуда файл смог бы скачать любой их читатель.

Известные уязвимости в зависимостях проверяются командой `just audit` (нужен
`cargo install cargo-audit`). В CI этой проверки нет намеренно: новая запись в базе advisory
появляется без всякого участия репозитория и уронила бы сборку на ровном месте.

## Сборка и проверки

Локально — `just clippy`, `just test`, `cargo fmt`; полный список в `justfile`.

На каждый push и pull request в `main` те же проверки идут в GitHub Actions
(`.github/workflows/ci_cd.yml`): `cargo fmt --check`, `cargo clippy --all-targets`,
`cargo doc --no-deps` с предупреждениями как ошибками, и сборка с тестами на Linux и macOS
для stable, nightly и 1.91. Nightly помечен `continue-on-error`: он ломается по причинам,
к коду отношения не имеющим.

Минимальная версия Rust — **1.91**, она же в `rust-version` манифеста. Ниже не собирается
`Duration::from_mins`.
